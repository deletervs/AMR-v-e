# 自主修复目标与能力缺口

记录日期：2026-10-08。状态：用户明确提出的项目目标与拟议方案，尚未实现。
现有能力判断基于 2026-10-07 源码快照，不代表已重新检查运行中的服务器或机器人。

## 用户的最终目标

机器人能够通过各种手段，包含软件操作、已登记硬件调用、未登记世界工具调用，修复自身产生的问题。修复没有人的主动介入。项目应尽量实现；至少看到雏形，并说明距离最终目的还缺什么。

“没有人的主动介入”在本项目中意味着：故障后不需要人先发现、输入修复指令、逐步诊断、选工具或手动操作；机器人自己完成闭环。人可以观察结果，也始终保留停止权。
部署前的授权、策略和环境准备，与运行时无需每次请人启动修复是不同问题。
如果超出可安全修复范围，机器人自主进入停止/隔离/允许的降级状态并记录失败，不把“等待人确认”当作修复成功。

开放世界任意故障全部自修复是研究方向，不是本项目现在能够保证的结果。能源耗尽、执行器不可用、缺少备件或工具、不可达部件、权限不足等，都可能使自主修复无法完成。
要逐层扩大可修复故障集合，明确每一层的能力和不可修复边界。

## 三类修复手段

| 类别 | 保留的目标 | 第一版边界 |
| --- | --- | --- |
| 软件操作 | 重连、重启组件、回滚配置/版本、替换后端；以后探索生成修复补丁并验证 | 只操作专用副本和自有测试进程；使用已审核动作，不执行模型随意生成的 shell |
| 已登记硬件 | 按能力描述调用备用传感器、可控电源、校准设备、机械臂或维修装置等 | 先用模拟硬件；只有实际具备且事先授权的设备才可进入真实执行 |
| 未登记世界工具 | 发现未预接入的外部软件工具、设备或实体物体，理解能做什么并形成操作方法 | 先在隔离环境使用未预绑定的 mock 工具；实体工具留作后续课题 |

第三类不是简单增加固定工具列表。需要从观察中形成能力假设，判断接口/接触方式、适用条件和风险，通过允许的低风险验证再使用。
“发现工具”不等于“获得权限”；临时适配或登记也不能自行扩大授权。未知第三方设备、校园共享服务器和不属于项目的资源默认不在修复权限中。
这里对“世界工具”的解释是暂定范围，后续可由用户细化；不得默默删掉未预接入工具这一最终目标。

## 两个并行闭环

任务闭环负责理解并完成人的目的；维护闭环负责让执行该目的的身体和软件保持可用。
同一个 `RobotState` 可供两者使用，但维护动作和任务动作需要仲裁，不能同时争抢设备或底盘。

```text
运行状态/异常证据
  -> 健康监测 -> 故障假设与诊断 -> 生成修复计划
  -> 权限/风险/预算检查 -> 暂停受影响任务并进入安全状态
  -> 执行修复 -> 独立验证 -> 恢复可用性并记录经验
                      |
                      +-> 失败：回退、换方案或结束尝试并保持安全
```

拟议状态机：`Healthy -> Suspect -> SafeHold -> Diagnosing -> Repairing -> Verifying -> Healthy / Degraded / Stopped`。
临时重连成功只是一个步骤；只有恢复了约定功能并通过观察窗口才算恢复。
`Degraded` 是否满足目标要另行声明，不能把停机、不断重启或只不再报错算作修复完成。

## 需要补齐的能力

| 缺口 | 为什么最终效果需要它 | 本项目的下一步 |
| --- | --- | --- |
| 可观察性 | 进程活着不等于相机、识别和控制正常 | 记录帧新鲜度、序号、错误、资源占用、命令确认和组件心跳 |
| 自身模型 | 必须知道组件、资源和依赖，才能定位故障影响 | 建立组件图、接口契约、版本/配置摘要及可用设备清单 |
| 诊断与因果判断 | 无帧可能来自网络、相机、agent 或格式错误，乱重启会误修 | 先做有限故障假设和排查步骤；记录证据与诊断置信度 |
| 修复动作契约 | 每个操作可能有副作用，需要知道何时能用 | 定义前置条件、预期效果、权限、资源锁、超时和回退 |
| 独立维护执行器 | 主识别或通信模块坏了，修复逻辑仍要运行 | 单独 supervisor；机器人本机安全保护不依赖服务器在线 |
| 成功验证 | 执行返回 0 或日志声称成功，不证明功能恢复 | 独立检查新帧、正确结果、持续健康和没有异常运动命令 |
| 事务与回滚 | 错误配置或半完成升级可能造成更大故障 | 可信基线、原子切换、版本快照与有限回退，保护原始源码 |
| 故障隔离与预算 | 反复重试可能耗尽能源、堵塞网络或形成重启循环 | 限制尝试次数、总时间、能耗和范围；失败后有限降级或停止 |
| 硬件反馈与冗余 | 无状态反馈的调用不能确认复位；单点损坏可能无替代路径 | 获取设备健康/动作反馈，再评估备用设备和可控复位能力 |
| 物理维修能力 | 接线、换件、清理遮挡等需要可达性、操作器、力觉和工具 | 核对现有硬件；按具体故障决定是否需要机械臂、维修底座或模块化部件 |
| 未登记工具理解 | 没有预设 API 时，必须推断用途、约束和可操作方式 | 先做未知 mock 工具发现与临时适配，之后再做物理工具感知与操作 |
| 自主代码修复 | 程序自身 bug 不能总靠重启消除 | 将候选补丁放在隔离副本，编译、回归、故障复测，再按策略发布；不在现场任意改生产代码 |
| 防止修复误判和越权 | 工具输出可能不可信；修复器不能改安全规则来“让测试过” | 独立权限检查、可信验证条件、审计和不可由修复流程改写的安全边界 |
| 长期经验与评测 | 同类故障要能复用经验，但不能把一次巧合当普遍方案 | 保存故障-证据-动作-结果记录；建立可重复故障集和留出测试 |

当前源码已有图像协议、状态记录和基本停止分支，可以作为监测入口；尚未形成上述自主诊断、修复执行、独立验证闭环。
快照中忽略读取 timeout、缺少 agent 命令过期保护等，是先完善故障检测和安全状态的具体切入点，不代表重启即可修复所有问题。

## 最小可展示雏形

第一版采用纯离线假机器人和自有子进程，不控制真实机器人，也不修改学校环境。
它是自主修复逻辑的演示，不声称已覆盖硬件维修或开放世界工具使用。

拟议组件：`HealthMonitor`、`FaultDiagnoser`、`RepairPolicy`、`RepairExecutor`、`RecoveryVerifier` 和事件记录。
第一版诊断/计划可以采用明确规则，大模型不是闭环成立的前提；之后再比较模型辅助诊断是否带来可量化收益。

| 故障注入 | 无人工修复动作 | 验证条件 |
| --- | --- | --- |
| mock 帧生产进程崩溃 | 自动检测死亡；有限次重启本项目拥有的子进程 | 新进程发出递增的新帧，经过健康观察窗口 |
| mock 进程仍在但帧冻结/陈旧 | 自动判断数据失效；保持零运动使能；重连或重启对应 mock 组件 | 时间和序号恢复前进，不接受旧帧伪装恢复 |
| mock 通道断开 | 按有上限的退避重连，不需要人手动运行重连命令 | 完整协议恢复，失败次数/时间受限 |
| 沙箱配置损坏 | 自动诊断并回滚到校验过的有效配置副本 | 配置校验、启动和功能测试通过，其他文件不变 |
| 持续不可恢复或动作不允许 | 自动停止尝试、隔离并记录原因 | 不无限重启、不扩大权限、不产生运动、不虚报成功 |

演示开始前允许设置参数和注入故障；故障发生到恢复/安全结束的过程不得人工敲修复命令。
验收预先写定检测时限、恢复时限、最大尝试次数和健康观察窗口，不把事后调阈值算作无人介入。
记录每轮故障、诊断证据、所选动作、验证结果、时间、失败原因和实际人工干预次数。
正向用例要恢复约定功能；负向用例要有界安全结束。未恢复必须计为修复失败，即使安全停止正确。
还要测试连续故障、误报、修复时再故障、supervisor 重启和人工停止，验证修复不会绕开任务授权。

## 从雏形到最终目标

1. 离线软件闭环：完成上面的故障注入与自主恢复演示。
2. 真实软件闭环：明确授权后，在独立部署中监测已有组件，加入独立安全保护与回滚验证；先不开放运动。
3. 已登记硬件闭环：针对一种实际可复现的硬件故障，接入健康反馈、有限复位或冗余切换，并验证恢复。
4. 未预接入工具雏形：在沙箱放入未绑定具体名称/接口的工具，通过有限允许的能力发现形成临时适配并解决一个故障；与完全固定工具选择区分。
5. 物理世界扩展：有对应操作硬件、环境模型和实验条件后，研究发现、选择、接近、操作外部工具完成一种具体物理修复。
6. 长期运行与泛化：用未见故障/工具组合测量能力边界，明确成功率、恢复代价和不可修复类别，而不是承诺任意故障都能修好。

阶段 4 的沙箱协议发现只是缩小问题后的雏形，不等于理解任意未知工具；阶段 3 的设备复位也不等于损坏零件的物理维修。
每个阶段展示“已实现什么、剩余什么、在哪些条件下失败”，持续向最终目标逼近。

## 权限与本次记录范围

自修复运行时可以在部署前定义的权限与预算内自主行动，不需要每次人工批准；超出边界则安全结束，不能把失败当作自动升权的理由。
修复器不能修改自己的权限、安全停止规则或验证标准来绕过故障；恢复功能也不自动恢复旧运动命令。
当前学校服务器是受限环境，真实硬件、共享系统文件和第三方设备不因记录这个目标而获得操作授权。

本次只更新目标、缺口和路线文档，没有实现修复程序、创建监控任务、改变机器人部署、执行硬件操作或提交推送。
